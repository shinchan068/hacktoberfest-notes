Give clear instructions, manage context and verify the output.

12 Prompts

In one line

The prompt is everything the model sees in one turn. Saying the goal, users, stack, must-haves and output gets much better results.

  • A prompt includes the task, rules, earlier messages and attached context.
  • System instructions are standing app rules; the user prompt is the current message.
  • State the goal, users, stack, must-have behavior and expected output. Better prompts help, but do not guarantee correctness.
Full notes & examples

A prompt is everything you send the model in one turn:

  • Your question or task.
  • Extra rules ("reply in JSON", "be short").
  • Earlier messages in the chat.
  • Files, code, or docs you paste or attach.

Many apps split this into:

  • a system prompt: standing instructions from the app, such as "You sort hostel complaints. Reply only in JSON."
  • a user prompt: the actual message, such as one complaint.

Better instructions usually give better results. They don't guarantee correct results, so you still need to check (Section 15).

Same model, better prompt

VagueClear
"make an app"Goal: sort hostel complaints by urgency. Users: wardens, on a phone. Stack: Next.js + Tailwind + a local open model. Must-have: paste text → cards showing category, room, urgency. Output: a working page + README steps.
You get a random app, the wrong tools, and unclear users.You get a first version close to what you need.

The stack is the set of tools and technologies you build with. Next.js and Tailwind are popular tools for building websites.

Check yourself

  1. List four things that can be part of a prompt.

    Reveal answer
    The task, extra rules, earlier messages, and attached files.

  2. What is the difference between a system prompt and a user prompt?

    Reveal answer
    The system prompt is the app's standing instructions. The user prompt is the actual message.

13 Prompt engineering: four habits

In one line

Be specific, give role, context, format and why, show an example with limits, then go in small steps and check every result.

  • Be specific: start with Build, Fix or Explain, and say what done means. Give role, context, format and why.
  • Show one or two small examples (few-shot prompting), plus constraints such as no paid APIs and no made-up packages.
  • Use null for missing room numbers. Work one step at a time, run the result, read the diff and verify uncertain or important output.
Full notes & examples

Prompt engineering means writing prompts on purpose. It isn't magic. It is giving clearer instructions so the model makes fewer mistakes.

What people typeWhat works better
"Build a hostel app"Goal + users + stack + output
"Fix my bug"The error message + the file + what you already tried
"Make it better"Clear limits: faster, works on mobile, no new libraries

Habit 1: Be clear and specific

Say exactly what "done" looks like.

  • Start with a verb: Build, Fix, Explain.
  • Name the stack and name the output you want back.
  • Avoid: "something cool with AI", "like Instagram but for hostels" (no scope), "make it better" (better how?).

Habit 2: Role, context, format, why

  • Role: who the model should act as, e.g. "a patient tutor".
  • Context: your situation, e.g. "first-year student, one evening, using a local model".
  • Format: how to reply, e.g. "a plan first, then code".
  • Why: the goal, e.g. "I need a demo that works".

Telling the model why helps it make better trade-offs.

Habit 3: Examples and constraints

  • Few-shot prompting means giving one or two small examples of the output you want.
  • Constraints are rules, such as: no paid APIs, no made-up packages, keep secrets out of Git.

Example: turning one complaint into structured JSON.

Input: "B block 204 no power since morning urgent"

{
  "category": "electricity",
  "priority": "high",
  "room": "B-204"
}

If the room number is missing, the model should return null (empty) for room instead of making one up. Your code should check the output, and a human should review uncertain or important cases.

Habit 4: Iterate and verify

Treat the model like a teammate and check its work. The first answer is a draft, and running the code is the real test.

  • Small steps: plan → one feature → the next feature.
  • Paste errors back into the chat instead of starting from zero every time.
  • Verify: run it, open the page, read the diff.
  • Chain prompts: "Now add tests", then "Now write the README", as separate prompts.

A complete example:

Build a mobile-friendly hostel complaint dashboard for wardens
using Next.js and Tailwind. Show category, room, urgency and status.
Use a local open-weight model to classify each complaint.
First propose the architecture; then build one complete flow with tests.
Check yourself

  1. What is few-shot prompting?

    Reveal answer
    Giving one or two small examples of the output you want.

  2. What are the four parts of Habit 2?

    Reveal answer
    Role, context, format, why.

  3. Why ask for null instead of a guessed room number?

    Reveal answer
    So the model doesn't invent data; an honest blank is better than a wrong room.

14 Tokens and the context window

In one line

Models read in tokens and can only see a limited amount at once, so give them only what matters.

  • A token is a text chunk, roughly three-quarters of an English word on average. Code and other languages can use more tokens.
  • The context window covers instructions, history, files and the model’s reply. When full, content may be cut, quality may drop or requests may fail.
  • Share relevant files, summarize logs and start a fresh chat when needed. Hosted APIs often bill for both input and output tokens.
Full notes & examples
  • A token is a chunk of text that a model reads and writes. On average, one token is about ¾ of an English word. Code and other languages often take more tokens. One token is not always one word.
  • The context window is the most text a model can handle at once: your prompt, the chat history, your files, and its reply. It is measured in tokens.
  • When it fills up: older messages or big files get cut off, answer quality drops, or the request is rejected.
  • Hosted APIs often charge per token, for both the input and the output.

Analogy: the context window is the size of a desk. Put on it only what you need. Don't dump the whole library on it.

Tips:

  • Share only the files that matter.
  • Summarize long logs instead of pasting all of them.
  • Start a fresh chat when a conversation gets long and confused.
Check yourself

  1. Roughly how many English words fit in 100 tokens?

    Reveal answer
    About 75.

  2. Does the model's reply use context window space?

    Reveal answer
    Yes.

  3. Your chat has become long and confused. What should you do?

    Reveal answer
    Start a fresh chat and share only what matters.

15 Hallucinations

In one line

A model can sound sure and still be wrong, so check names, links and facts against official sources and by running the code.

  • A hallucination sounds confident but is false: a nonexistent package, fake API, wrong fact or broken link.
  • Models predict plausible text without automatically checking facts. A suggested package name can also become an attacker’s trap.
  • Check official registries and documentation, read commands before running them, open sources and test real output.
Full notes & examples

A hallucination is output that sounds confident but isn't true. Examples: a package that doesn't exist, a fake API, a wrong fact, or a broken link.

Why it happens: a model predicts text that sounds right. It does not automatically check facts.

A real case

An AI model told people to run pip install huggingface-cli, but no package with that name existed. (pip is Python's tool for installing packages. PyPI is the official place Python packages come from, and npm is the same thing for JavaScript.) A researcher then uploaded an empty package with that exact name, and it got more than 15,000 real downloads in 3 months. (Source: The Register, 28 March 2024.)

Lesson: check a package name on PyPI or npm before you install it. A fake name wastes your time. A malicious one, made by an attacker, can do real damage.

How to protect yourself

  • Check package and API names on the official registry and in the docs.
  • Run the code and tests, and look at the real output.
  • Trust official docs over "the model said so".
  • Don't run commands you haven't read, especially ones that delete files, change permissions, or could expose keys.
  • When a fact matters, ask for a source and open it yourself.
Check yourself

  1. Why do models hallucinate?

    Reveal answer
    They predict text that sounds right and don't automatically check facts.

  2. What should you check before running pip install on a package an AI suggested?

    Reveal answer
    That the package really exists on PyPI or npm, by reading its official page.
