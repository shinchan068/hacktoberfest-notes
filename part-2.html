Part 2 — Open source, licenses and Git

Understand licenses and make a useful first contribution.

06 How open-source software works

In one line

Open source means public code plus an open license. You contribute by opening issues and pull requests that maintainers review and merge.

  • Open-source software combines public source code with an open-source license. Maintainers review contributions; contributors help in many ways.
  • Read README, CONTRIBUTING.md and the Code of Conduct. Find a needed issue before making a focused change.
  • Fork → branch → change → PR → review → merge. Useful documentation and tests count as contributions; avoid PRs made only to get counted.
Full notes & examples

Open-source software is software whose source code is public and comes with an open-source license that lets anyone use, study, change, and share it. Linux, Python, and VS Code's core code are well-known examples.

Who's who

  • Maintainers: the people who run a project. They review and accept changes.
  • Contributors: anyone who helps. That can mean fixing bugs, writing docs, adding tests, or answering questions.
  • Users: people who use the software.

Words you'll meet on GitHub

  • Issue: a public note about a bug, an idea, or a question.
  • Fork: your own copy of someone else's repository, under your account.
  • Branch: a separate line of work inside a repo (see Section 8).
  • Pull request (PR): a request asking the maintainers to accept your changes into their project.
  • Review: maintainers read your PR and ask questions or request changes.
  • Merge: your change is accepted and joined into the main code.

A typical first contribution

  • Find a project you use, and read its README and CONTRIBUTING.md (the guide for contributors).
  • Look for issues labelled good first issue.
  • Comment to say you'd like to work on it, and wait for a reply if the project asks you to.
  • Fork the repo, create a branch, and make a small, focused change.
  • Open a PR that explains what you changed and why. Link the issue it fixes.
  • Reply to the review politely and update your PR.

Projects also often have a Code of Conduct, the rules for respectful behaviour.

Good contributions are small, tested, and actually needed. Low-effort PRs, such as changing one word only to get a PR counted, waste maintainers' time.

Check yourself

  1. What is the difference between a fork and a branch?

    Reveal answer
    A fork is your own copy of someone's repo. A branch is a line of work inside one repo.

  2. Which file explains how to contribute to a project?

    Reveal answer
    CONTRIBUTING.md.

  3. What makes a good first PR?

    Reveal answer
    Small, focused, tested, actually needed, and explained clearly.

07 Licenses

In one line

No LICENSE means no permission to reuse. MIT and Apache-2.0 are permissive, GPL is copyleft and applies when you distribute, and your model's license is separate from your code's.

  • Public code without a LICENSE gives no automatic permission to copy, change or share it.
  • MIT and Apache-2.0 are permissive with conditions. GPL-3.0 is copyleft: source-sharing duties apply when distributing, not just making private changes.
  • Your app’s license and model’s terms remain separate. Check dependencies, copied code, images and datasets too. This is learning material, not legal advice.
Full notes & examples

A license is a short text file in a repo (usually named LICENSE). It says what others are allowed to do with the code or model, and on what conditions.

  • Copyright (the creator's legal right over their work) applies to code even when anyone can see it.
  • So public on GitHub does not mean free to reuse. Without a LICENSE, others generally get no automatic permission to copy, change, or share the code.
  • Public code with no LICENSE is only public. It is not open source.

Three licenses to recognize

LicenseIn simple wordsRemember
MITDo almost anything: use, change, share, even sellKeep the copyright and license notice. Short and simple.
Apache-2.0Like MIT, with extra wording about patentsKeep notices, and mark the files you changed
GPL-3.0"Copyleft": if you give the program (or a changed copy) to others, you must also give them the source code under GPLThe duty applies when you distribute it. Changing it for your own private use doesn't force you to publish anything.
  • A patent is a legal right over an invention.
  • Permissive licenses (MIT, Apache-2.0) have few conditions.
  • Copyleft licenses (GPL) require that anyone who passes the software on keeps it under the same open terms.

Your code's license and your model's license are separate

Suppose your app's code is MIT and it uses Gemma. Gemma has its own terms, which are not MIT. Your MIT license does not replace the model's license. Name both in your README:

Application code: MIT License (see LICENSE)
AI model: [exact model ID]
Model source: [official model card URL]
Model terms: [license/terms URL]

Adding a LICENSE on GitHub: in your repo, create a new file named LICENSE, and GitHub will offer license templates. The website choosealicense.com explains each license in plain words.

Before you choose a license, check the code you copied, your dependencies, any datasets and images, and the model's terms. You cannot put your own license on material you don't own.

(This section is for learning. It is not legal advice.)

Check yourself

  1. A repo is public but has no LICENSE. Can you freely copy its code?

    Reveal answer
    No. There is no automatic permission.

  2. When do GPL's "share the source" duties apply?

    Reveal answer
    When you distribute the program or a changed copy.

  3. Your app is MIT and uses Gemma. Is Gemma now under MIT?

    Reveal answer
    No. Gemma keeps its own terms.

08 Git and GitHub

In one line

Git tracks changes as commits, GitHub hosts them online, and the everyday loop is status → add → commit → push.

  • Git records changes; GitHub hosts repositories and collaboration. A commit is a snapshot with a message; a branch is a line of work.
  • Everyday loop: git status → git add → git commit → git push. A remote is an online copy, conventionally called origin.
  • Review staged changes, keep commits focused and ignore .env, dependencies and build output. .gitignore does not remove files already tracked.
Full notes & examples
  • Git is a tool that records every change you make to a project, so you can see history, undo mistakes, and work with others.
  • GitHub is a website that stores Git projects online and adds issues, pull requests, and reviews.
  • A repository (repo) is a project folder tracked by Git.
  • A commit is a saved snapshot of your changes, with a message describing them.
  • A branch is a separate line of work. main is usually the default branch. You make a new branch to try a feature without breaking main.
  • A remote is the online copy of your repo, usually on GitHub. By convention it is called origin.

Basic commands

git init                     # start tracking this folder
git status                   # see what changed
git add .                    # pick all changes for the next commit
git commit -m "Add complaint classifier"
git remote add origin <repository-url>
git push -u origin main      # upload commits to GitHub

Other everyday commands:

git clone <repository-url>   # download a repo to your computer
git pull                     # get the latest changes from GitHub
git checkout -b new-feature  # create and switch to a new branch
git log --oneline            # see the commit history

Good habits

  • Run git status before every commit, so you don't add secret or junk files.
  • Use a .gitignore file to list what Git must never track, such as .env, node_modules/, and build folders.
  • Make small commits with clear messages, like "Add room number validation", not "stuff".
  • Commit often. Your history shows how the project grew and lets you go back if something breaks.
Check yourself

  1. What is a commit?

    Reveal answer
    A saved snapshot of changes, with a message.

  2. Which command shows what will go into your next commit?

    Reveal answer
    git status.

  3. Why should .env be listed in .gitignore?

    Reveal answer
    So real keys never get committed.

09 Project structure and the README

In one line

Keep a clear folder layout, and write a README that lets a stranger understand, set up, and run your project.

  • Use a clear layout: frontend/, backend/, tests/, README.md, LICENSE, .gitignore and .env.example.
  • The README explains the problem, users, features, model role, exact model ID, source and terms.
  • Include setup, run and test steps, known limits and the app license. Commit fake values in .env.example, never real keys in .env.
Full notes & examples

A simple project layout

Many small AI web apps look roughly like this:

my-app/
  README.md         ← what it is and how to run it
  LICENSE           ← reuse permissions
  .gitignore        ← files Git must ignore
  .env.example      ← fake keys showing what is needed
  frontend/         ← pages the user sees
  backend/          ← server code, calls the model
  tests/            ← automatic checks

Exact folder names depend on your tools. What matters is that a new person can find things.

README checklist

A README is the front page of your repo. A good one includes:

  • What problem it solves and who it is for.
  • Features, and what the AI model does in it.
  • The exact model ID, its source, a link to its license or terms, and how it runs (locally or through an API).
  • Setup steps, including "copy .env.example to .env".
  • How to run it and how to test it.
  • Known limitations.
  • The app's license.
Check yourself

  1. Name four things a README should contain.

    Reveal answer
    Any four: what it does and for whom, features and the model's role, model ID, source and license, setup steps, how to run and test, limitations, the app license.

  2. Why commit .env.example but not .env?

    Reveal answer
    .env.example holds only fake values that show what's needed. .env holds real secrets.
