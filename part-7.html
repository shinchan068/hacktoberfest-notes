20 Worked example: Hostel Complaint Triage

In one line

Build one complete flow first: messy message in → model → checked JSON → card on screen.

  • For wardens and floor representatives: turn messy complaints into category, priority, room and a short summary, with human correction.
  • Build one complete flow: submit → backend calls model → JSON → validation → dashboard. Authenticate users and validate before saving.
  • Choose an open-weight model that works on realistic messages within your hardware, budget and license. Missing room means null; do not invent it.
Full notes & examples

Problem: hostel complaints arrive as messy chat messages, with slang, missing room numbers, and urgent and non-urgent issues mixed together. Wardens sort them by hand, and important issues get buried.

Users: hostel wardens and floor representatives.

Goal: a warden pastes a batch of complaints and gets a sorted list showing the issue, its urgency, the room, and a one-line summary, so they can skim it in under a minute.

The smallest version that works (MVP)

An MVP (minimum viable product) is the smallest version that really works. Here it is one flow:

  • The warden submits a messy message.
  • The backend sends it to an open-weight model.
  • The model suggests the category, priority, and room as JSON.
  • The backend checks the JSON (validation).
  • The dashboard shows the card and lets the warden correct it.
Browser dashboard
   ↓
Backend API (validation + auth)
   ↓
Open-weight model (local runner or hosted endpoint)
   ↓
JSON → validation → database → dashboard

Auth (authentication) means checking who the user is. A database is where an app stores its data permanently.

What the backend call can look like

A small sketch in JavaScript, calling a local model through Ollama's API. The model name is a placeholder.

const res = await fetch("http://localhost:11434/api/generate", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    model: "<model-name>",
    prompt: "Classify this hostel complaint. Reply only with JSON " +
            "with keys category, priority, room (null if missing): " +
            complaintText,
    format: "json",
    stream: false
  })
});
const data = await res.json();
const card = JSON.parse(data.response); // then validate card

What it does: it sends a POST request with the prompt, asks for JSON, waits for the full answer (stream: false), and reads the model's text from data.response. After that, your code must still check that category, priority, and room make sense.

Choosing the model

Pick a model that reliably labels short, noisy messages, runs on the hardware and budget you have, and is legally usable under its terms. Test it on realistic complaints before building a fancy interface. If the model can't do the job, a nice UI won't save the project.

Check yourself

  1. List the five steps of the MVP flow.

    Reveal answer
    Submit message → backend sends it to the model → model returns JSON → backend validates it → dashboard shows the card and allows correction.

  2. In the code sketch, why is JSON.parse not the last step?

    Reveal answer
    The model's JSON can still have missing or wrong values, so you must validate it.

21 Testing an AI app

In one line

Test the messy and failing cases, not only the happy path, and prove that the model's answers are live.

  • Test clear complaints, missing rooms, slang, typos, duplicates and mixed urgency signals.
  • Handle timeouts and invalid JSON with a useful error or retry. Do not crash or save bad data. Prove that new input gets live model output.
  • Try a fresh setup using only the README. Before sharing: working repo, licenses recorded, live AI feature, no secrets and an explanation of your choices.
Full notes & examples

Testing means checking, on purpose, that your app behaves correctly, including in bad situations. For an AI feature, test the strange cases as well as the happy path (the case where everything goes right).

Using the triage example:

  • A normal complaint with a clear room number.
  • A complaint with no room number: the model must not invent one.
  • Slang, typos, duplicate messages, and mixed-up urgency signals.
  • The model being slow (a timeout, where you give up waiting after a set time) or returning invalid JSON. Your app should show a helpful error, not crash.
  • A new input gives a live answer from the model, not a hardcoded (fixed, pre-written) answer.
  • A fresh setup: follow only your README steps on a clean machine and check it runs.

Final check before sharing a project:

  • Public repo with a working README.
  • The right app LICENSE, and the model's terms recorded.
  • The AI feature really works on new input.
  • No secrets committed.
  • You can explain how it works and why you made your choices.
Check yourself

  1. Name three tricky inputs to test in a triage app.

    Reveal answer
    Any three: no room number, slang or typos, duplicates, mixed urgency signals.

  2. What should your app do if the model returns invalid JSON?

    Reveal answer
    Show a clear error or retry, and not crash or save bad data.
