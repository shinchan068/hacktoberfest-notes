Part 8 — Vibe coding case study

How yesterday’s HostelHub session moved from a rough idea to tested, reviewable pull requests.

22 Start with the problem, not a magic prompt

In one line

Explain your understanding, ask the model to challenge it, and reduce the result to a small MVP before writing production code.

  • The real problem was not “build a dashboard”; it was that genuine hostel complaints disappeared inside noisy WhatsApp conversations.
  • Antigravity was first used as a product-thinking partner: correct assumptions, identify users, choose the MVP and cut unnecessary screens.
  • The approved MVP connected four things: import and triage, a complaints board, complaint details and WhatsApp work-order export.
Full notes & recovered prompt

The session began with a long explanation of how students report problems, why P0 issues can still be missed, and how a warden might paste a chat dump into a new tool. That explanation was more useful than asking an agent to “make an app” because it gave the model a problem to evaluate.

A cleaner version of the opening prompt

I am building a student project for hostel issue management.

Students report maintenance problems in a busy WhatsApp group. Genuine
complaints are mixed with casual chat, some messages omit the room number,
and urgent issues can be missed.

My idea is to let a warden paste a chat dump, extract genuine complaints,
assign category and priority, and track them on a board.

Do not simply agree with me. Tell me:
1. What have I understood correctly?
2. Which assumptions are weak or incorrect?
3. What is the smallest demo-ready MVP?
4. What should be deferred?

Do not build the application yet.

This produced a product verdict before implementation. It also exposed an important wording correction: Gemma should be described as an open-weight model, while the API platform and exact model ID should be recorded separately.

Check yourself

  1. Why is “build me a hostel dashboard” a weak first prompt?

    Reveal answer
    It describes a screen, not the real users, pain points, workflow, constraints or definition of success.

  2. What four capabilities formed the approved MVP?

    Reveal answer
    Import and triage, complaints board, complaint details, and WhatsApp work-order export.

23 Carry context through files, not chat memory

In one line

New chats become reliable when the decisions live in product, design and build documents inside the project.

  • Antigravity handled early product thinking, wireframes, design review, specification and planning.
  • Codex handled most phased implementation, debugging, tests, Git branches and pull requests.
  • The handoff worked through PRODUCT_SPECIFICATION.md, DESIGN.md, Build_PLAN.md, screenshots, source code and Git history—not automatic chat synchronization.
Full notes & handoff prompt

The first Antigravity conversation created the product direction and phased plan. A second Antigravity conversation initialized the project. The implementation later continued in Codex. Each tool could inspect the same project files, so the documents became the shared memory.

Reliable new-chat handoff

Read these before doing anything:
- PRODUCT_SPECIFICATION.md
- DESIGN.md
- Build_PLAN.md
- the supplied design screenshots
- the existing source and Git status

Summarize the current scope and the requested phase. Point out any conflict
between the documents and the code. Then implement only Phase [number].
Do not start the next phase automatically.

Project evidence is available in the Hostel-Demo repository. The completed phase branches were reviewed through the project’s pull requests.

Check yourself

  1. Which three documents carried the main product context?

    Reveal answer
    PRODUCT_SPECIFICATION.md, DESIGN.md and Build_PLAN.md.

  2. Did Antigravity and Codex need automatic chat synchronization?

    Reveal answer
    No. They recovered the important context from shared project files, source code and Git history.

24 Build one phase, test it, then merge it

In one line

Vibe coding becomes engineering when each AI-assisted change is bounded, tested and saved as a reviewable Git checkpoint.

  • Before each phase, the agent read the plan and gave a short implementation summary; the user then approved the bounded work.
  • Each meaningful phase used a feature branch, focused verification, a pull request and a merge to main.
  • The real Gemma integration came after the demo workflow worked, which reduced API cost and made failures easier to isolate.
Full notes & implementation loop
Choose one phase
      ↓
Read spec + design + existing code
      ↓
Summarize the intended change
      ↓
Create a feature branch
      ↓
Implement the smallest complete phase
      ↓
Run focused tests and browser checks
      ↓
Push → pull request → review → merge
      ↓
Start the next phase

A reusable implementation prompt

Read PRODUCT_SPECIFICATION.md, DESIGN.md, Build_PLAN.md and the existing code.

Implement only Phase [number/name]. Before editing, summarize your approach
in four bullets.

Preserve existing behavior, reuse current components, do not add deferred
features, keep secrets server-side, and run the smallest relevant tests.
Report the changed files, verification evidence and any manual checks.

The repository records seven merged pull requests covering import and triage, planning updates, complaint details, work-order export, Gemma integration, polish and the Overview dashboard.

When debugging, replace a vague “fix it” with the error, reproduction steps, expected behavior and a request for the smallest correct change.

Check yourself

  1. Why was the real model connected after the demo workflow?

    Reveal answer
    The UI and data flow could be built and tested without spending model quota, and API failures stayed isolated to one later phase.

  2. What should happen before a phase is merged?

    Reveal answer
    The bounded feature should be implemented, tested, reviewed in a pull request and checked against its acceptance criteria.

Quick Hack Day checklist
  • Record the exact model ID, provider, source URL and model terms.
  • Add an application LICENSE and keep secrets out of Git.
  • Create .env.example with fake placeholder values.
  • Give your coding agent the specification, design rules and current library docs.
  • Build one working end-to-end path before adding extra screens.
  • Test new input, missing information, invalid model output, timeouts and empty states.
  • Make sure you can explain every important choice without the agent.
Check yourself

  1. Which resource helps you choose an application license?

    Reveal answer
    Choose a License at choosealicense.com.

  2. What is Context7 useful for?

    Reveal answer
    It supplies current library documentation so the agent is less likely to guess outdated APIs.

  3. Does MCP replace the open-weight model used by your product?

    Reveal answer
    No. MCP connects the agent or app to tools; the product’s model is a separate architectural choice.
